# LightRAG Enterprise Document Parser（EDP）

## Design Proposal V1.0

> **目标**
>
> 在不修改 LightRAG Graph 和 Hybrid Retrieval 的前提下，新增一套适用于企业文档的解析能力，实现：
>
> * 基于标题结构的 Chunk 切分
> * Embedding Context 增强
> * Metadata Template
> * Milvus Metadata Filter

---

# 1. 设计目标

目前 LightRAG 已支持多种 Chunk Strategy，但企业知识库中的文档（研究报告、周报、公文、技术文档等）通常具有明确的标题层级。

V1 新增一种面向企业文档的 Document Parser，提供：

* Structure-aware Chunk Strategy
* Context Builder
* Metadata Template
* Metadata Filter

保持 Graph、Entity Extraction、Hybrid Retrieval 完全不变。

---

# 2. 总体架构

```text
                 Document
                     │
                     ▼
            Document Parser（新增）
                     │
    ┌────────────────┼────────────────┐
    ▼                ▼                ▼
Structure Chunk   Context Builder   Metadata Builder
    │                │                │
    └────────────────┴────────────────┘
                     │
                     ▼
                LightRAG
          (Embedding + Graph)
```

Document Parser 为新增模块。

LightRAG 原有流程无需修改。

---

# 3. Document Parser

Document Parser 包含三个模块：

## 3.1 Structure-aware Chunking

负责文档切分。

## 3.2 Context Builder

负责构造 Embedding Text。

## 3.3 Metadata Builder

负责生成 Metadata。

---

# 4. Structure-aware Chunk Strategy

新增一种 Chunk Strategy：

```yaml
chunk_strategy: structure
```

处理流程：

```text
Document
      │
Heading Detection
      │
Heading Tree
      │
Section
      │
Section > MaxToken ?
      │
      ├── No
      │      │
      │      ▼
      │   One Chunk
      │
      └── Yes
             │
        List Split
             │
      Paragraph Split
             │
      Sentence Split
```

---

切分规则：

Rule 1

Chunk 不允许跨章节。

Rule 2

优先保持章节完整。

Rule 3

只有章节超过 MaxToken 才继续递归切分。

Rule 4

切分优先级：

```text
Section

↓

List

↓

Paragraph

↓

Sentence
```

---

# 5. Context Builder

每个 Chunk 保留两个字段：

```text
chunk_text
```

原始内容。

```text
embedding_text
```

用于向量化。

构造方式：

```text
Document Title

↓

Heading Path

↓

Chunk Text
```

例如：

```text
Document:
GD1265研究报告

Heading:
实验结果 > EQE测试

Chunk:
EQE达到26%
```

Embedding：

```text
GD1265研究报告

实验结果 > EQE测试

EQE达到26%
```

Graph 与 Entity Extraction 仍使用：

```text
chunk_text
```

保证原文不变。

# 6. Metadata Template

不同类型文档维护不同 Template。

例如：

```text
templates/

    research_report.yaml

    weekly_report.yaml

    patent.yaml

    meeting.yaml
```

Template 示例：

```yaml
document_type: research_report

description: OLED研究报告

chunk_strategy:
  type: structure
  max_token: 1200

context_builder:
  include_document_title: true
  include_heading_path: true

metadata:

  fields:

    material:
      type: string
      source: document

    customer:
      type: string
      source: document

    project:
      type: string
      source: document

    heading_path:
      type: string
      source: heading

    knowledge_type:
      type: string
      source: heading

    experiment:
      type: string
      source: llm

    conclusion:
      type: string
      source: llm

    keywords:
      type: array
      source: llm
```

---

# 7. Metadata Source

Metadata 字段来源固定四种：

| Source   | 来源       | 是否调用LLM  |
| -------- | -------- | -------- |
| document | 文档整体     | 是（一次）或规则 |
| heading  | 标题树      | 否        |
| llm      | Chunk 内容 | 是        |
| rule     | 正则规则     | 否        |

说明：

## document

只提取一次。

例如：

```json
{
    "material":"GD1265",
    "customer":"BOE"
}
```

后续所有 Chunk 继承。

---

## heading

自动生成。

例如：

```json
{
    "heading_path":"实验结果/EQE",
    "knowledge_type":"实验结果"
}
```

无需调用 LLM。

---

## llm

根据 Chunk 内容补充。

例如：

```json
{
    "experiment":"EQE",
    "keywords":[
        "EQE",
        "LT95"
    ]
}
```

---

## rule

通过正则、自定义函数生成。

例如：

日期

作者

项目编号

等。

---

最终每个 Chunk Metadata：

```json
{
    "document_type":"research_report",

    "material":"GD1265",

    "customer":"BOE",

    "heading_path":"实验结果/EQE",

    "knowledge_type":"实验结果",

    "experiment":"EQE",

    "keywords":[
        "EQE",
        "LT95"
    ]
}
```

最终 Metadata 存储到 Milvus。

# 8. Document Import

新增导入接口。

示例：

```http
POST /documents/import
```

请求：

```json
{
    "template":"research_report",

    "files":[
        "A.docx",
        "B.docx",
        "C.docx"
    ]
}
```

说明：

* template 为 Template 名称。
* 一次导入支持多篇文档。
* 同一批文档共用一个 Template。
* Parser 根据 Template 完成整个解析流程。

---

导入流程：

```text
Import

↓

Load Template

↓

Document Parser

↓

Chunk

↓

Milvus

↓

Graph
```

# 9. Query Retrieval

检索接口新增 Metadata 参数。

流程：

```text
Question

↓

Metadata Parser

↓

Metadata Filter

↓

Milvus ANN Search

↓

LightRAG Graph Retrieval

↓

LLM
```

例如：

用户：

> GD1265实验结果

Metadata Parser：

```json
{
    "material":"GD1265",

    "knowledge_type":"实验结果"
}
```

Milvus：

```text
material=="GD1265"

&&

knowledge_type=="实验结果"
```

过滤后进行向量检索。

推荐：

Soft Filter。

过滤为空：

自动退化普通向量检索。

# 11. Design Principles

1. 不修改 Graph 构建流程。
2. 不修改 Entity Extraction。
3. 新增一种 Chunk Strategy，不影响已有 Strategy。
4. Metadata 最终存储在 Chunk 上，兼容 Milvus Scalar Filter。
5. Embedding 使用 embedding_text，Graph 使用 chunk_text。
6. 所有能力均支持配置开关。
7. 一个 Template 定义一种文档类型的完整解析策略（切分、上下文增强、元数据提取）。

# 12. V1 范围

**实现内容：**

* ✅ Structure-aware Chunk Strategy
* ✅ Context Builder
* ✅ Metadata Template
* ✅ Metadata Builder
* ✅ Metadata Filter（Milvus）
* ✅ 批量导入（同 Template）

**暂不实现：**

* Parent Summary
* Knowledge Unit
* Graph Metadata
* Query Rewrite
* Query Intent Parser

# 我建议再做一个小调整（也是我认为整个方案最后一个可以优化的地方）

我建议**不要把 Template 和 Document Type 强绑定**，而是把 Template 定义为**Parser Profile（解析配置）**。

例如：

```yaml
template: oled_research_v1
```

而不是：

```yaml
template: research_report
```

因为未来企业很可能有多个"研究报告"模板：

* `oled_research_v1`
* `oled_research_customer`
* `oled_research_internal`

它们都是研究报告，但字段不同、切分策略不同、Prompt 不同。

也就是说，**Template 更准确的含义应该是"一种解析配置（Parser Profile）"，而不是"一种文档类型"。**

这样后续扩展几乎不需要改架构，只需要新增一个 YAML 配置即可。我认为这是整个方案最后一个值得采纳的优化点。
